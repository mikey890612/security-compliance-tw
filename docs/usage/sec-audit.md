# sec-audit 使用說明

**找出會被掃描器標紅字的地方，在送掃之前修掉；或拿到掃描報告後判讀誤判。**

---

## 什麼時候用

| 情境 | 用哪個模式 |
|---|---|
| 系統快要送資安檢測，想先自己過一遍 | 模式 1 |
| 剛拿到 Fortify / Checkmarx / AWVS 報告，一堆紅字不知道哪些是真的 | 模式 2 |
| 驗收被打回來，要逐項回覆稽核意見 | 模式 2 |
| 接手別人的專案，想知道資安體質 | 模式 1 |

**判斷規則很簡單：手上有掃描報告檔案就是模式 2，沒有就是模式 1。**

---

## 怎麼觸發

在專案根目錄開 Claude Code，然後任一種說法都可以：

```
/sec-audit
```

```
幫我看一下這個專案送掃會不會過
```

```
我有一份 Fortify 報告，幫我判讀哪些是誤判
```

```
下週要資安驗收，先自己檢查一遍
```

**重要：從專案根目錄啟動 Claude Code。** 產出會寫在啟動時的工作目錄下，
不是你後來 `cd` 過去的目錄。

---

## 它會問你什麼

**一次問完三題**，用複選壓縮成三個問答，不會逐題來回：

**第 1 題 — 安全分級**：普 / 中 / 高

> 依「資通安全責任等級分級辦法附表九」由機關核定。
> 不確定的話查驗收文件；真的查不到就選「中」，它會在報告首頁註明這是假設。

**第 2 題 — 專案特性**（複選，全不勾也可以）

- 對外提供服務
- 有 API 端點
- 有 LLM / RAG / Agent 功能
- 處理個人資料或金流
- 有行動 App（iOS／Android 原生）
- 有 EMM／MDM／MAM

**第 3 題 — 已知會面對哪些掃描器**（複選，可選「不知道」）

- 商用 SAST（Fortify / Checkmarx）
- 開源 SAST（Semgrep / SonarQube / CodeQL / gosec / bandit）
- DAST / 弱點掃描（AWVS / Nessus / ZAP / WebInspect）

**「有沒有登入功能」它不會問**——那個從程式碼看得出來，它會自己判定。

### 這幾題會影響什麼

答案決定它載入哪些檢查項目。舉例：

| 你的答案 | 載入 | 不載入 |
|---|---|---|
| 中 · 對外服務 · 無 API · 無 AI · 無個資 | 注入、錯誤處理、存取控制、密碼學、三個 DAST 類 | API 授權、LLM、日誌稽核、MAST、MDM |
| 中 · 對外服務 · 無 API · 無 AI · **有個資** | 上列 **＋ 日誌與稽核** | API 授權、LLM、MAST、MDM |
| 中 · … · **有行動 App** | 上列適用項 **＋** `mast-storage-crypto`、`mast-network-ipc` | （無 App 時不載入） |
| 中 · … · **有 EMM／MDM／MAM** | 上列適用項 **＋** `mdm-controls` | （無 MDM 時不載入） |

**第二列多出來的「日誌與稽核」在實測中抓到了一個沒有任何掃描器會報的問題**
（稽核事件完全缺席）。少答一題就整類漏掉，所以照實回答。

## 模式 1：送掃之前

### 它會做什麼

1. 問你上面三題
2. 讀 `go.mod` / `requirements.txt` / `package.json` 判斷語言
3. 依你的答案挑出要查的類別，**只載入需要的**
4. 用每個檢查項的「壞味道樣式」在程式碼裡搜尋
5. 逐項判定：真漏洞 / 誤判 / 不適用
6. **列出待修清單，等你確認才動手改**
7. 寫出報告

### 你會拿到什麼

```
security-audit/
├── findings.md          逐項：編號 / 位置 / 判定 / 修法 / 掃描器預期會標什麼
└── false-positives.md   誤判清單與佐證
```

`findings.md` 的每一項長這樣：

- **位置**精確到行號
- **判定理由**寫明為什麼是真漏洞或誤判
- **掃描器預期**列出哪些工具會標、標什麼名字、什麼等級
- **過關寫法**可以直接抄的修補程式碼

範例見 [`examples/audit-findings.md`](../../security-compliance-tw/examples/audit-findings.md)。

### 修補的分寸

**它不會直接大改你的程式碼。** 修補前一定先列清單與影響檔案數，
等你點頭。優先序是「掃描器等級 × 你的專案分級」算出來的：

| 掃描器等級 | 分級高 | 分級中 | 分級普 |
|---|---|---|---|
| Critical / Blocker | P0 | P0 | P0 |
| High | P0 | P1 | P1 |
| Medium | P1 | P2 | P2 |
| Low / Info | P2 | P3 | P3 |

P0 是送掃前必修。P3 可以在報告裡列為「已知、不修」並附理由。

## 模式 2：拿到掃描報告之後

### 怎麼給它報告

把報告檔放進專案目錄，然後說：

```
這是 Fortify 掃出來的報告，幫我看哪些是誤判
```

**格式支援度**：csv / txt 最好，html / pdf 盡力解析。
Fortify 的 `.fpr` 是壓縮格式，請先從 Audit Workbench 匯出成 csv。

### 它會做什麼

1. 解析報告，取出每項的規則名稱、等級、檔案位置
2. 用規則名稱反查對應的檢查項
3. 依該項的「判定準則」逐項判定
4. 真漏洞給修法；誤判產出佐證
5. 找不到對應的項目會**明說「本知識庫尚未涵蓋」**，不會亂猜

### 誤判的判定標準

它不會隨便說「這是誤判」。要同時滿足三點：

1. 資料實際不可控（來源是常數、列舉，或已通過白名單驗證）
2. 路徑上確實有消毒或參數化，只是工具追不出來
3. 有具體佐證：檔案位置、資料來源、消毒點行號

**三點缺一就當真漏洞修。**

`false-positives.md` 會寫成可以直接貼進 Fortify Audit Workbench 或
Checkmarx 的「Not Exploitable」說明欄的形式。各工具的標記方式
（`#nosec`、Not an Issue 等）它會一併告訴你。

---

## 它不會做的事

| 不做 | 為什麼 |
|---|---|
| **執行任何掃描工具** | 掃描由人執行。它做的是預判與判讀 |
| 對線上系統發動 DAST 探測 | 滲透測試須先取得書面授權 |
| 產生附表十查檢表、測試報告等交付文件 | 那是 `sec-deliverables` 的工作 |
| 檢查基礎設施（GCB、防火牆、OS 加固） | 不在範圍 |

DAST 類的檢查它是**看程式碼預判**——檢查 middleware 註冊、標頭設定、
Cookie flags、TLS 組態，推斷掃描器會看到什麼，而不是真的去打你的系統。

---

## 已知限制

**樣式比對不等於污點分析。** 以下情形可能漏判：

- 不安全操作被包進多層 helper 函式（跨函式資料流追不到）
- 動態組成、執行期才危險的字串
- 二階注入（資料先寫進資料庫，稍後取出使用）

**所以「未命中」不等於「沒有這個問題」。** 報告裡會寫明這條限制。

另外，商用工具（Fortify / Checkmarx）的規則名稱來自模型知識，
**未與真實掃描報告核對過**。開源工具（gosec、bandit、SonarQube、
Semgrep、CodeQL）的規則編號已人工核對。

## 常見問題

**Q：分級不知道怎麼辦？**
選「中」。它會在報告首頁註明是假設，並說明核定為「高」時會多出哪些項目。

**Q：它說某項「本知識庫尚未涵蓋」，怎麼辦？**
目前 43 則檢查涵蓋不到備份備援、稽核容量、時戳校時、系統文件、委外管理、
供應鏈完整性、基礎設施加固。這些要另循管道處理，它不會憑印象生成建議。

**Q：跑第二次會覆蓋第一次的報告嗎？**
會。要保留就先改名或複製走。

**Q：可以只查某一類嗎？**
可以，直接說「只看注入類」或「只查 API 授權」。
