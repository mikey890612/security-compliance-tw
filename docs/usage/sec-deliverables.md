# sec-deliverables 使用說明

**把技術結果變成稽核人員看得懂、驗收時交得出去的文件。**

`sec-audit` 找問題修問題，這支把結果轉成文件。

---

## 六種文件

| 文件 | 用途 | 需要先跑 sec-audit 嗎 |
|---|---|---|
| **附表十安全查檢表** | 驗收勾稽，逐項標符合與否 | **要** |
| **源碼安全查檢表** | 九大類源碼層檢核 | **要** |
| **安全測試報告** | 證明做過檢測、誤判有佐證 | **要** |
| **威脅建模** | DFD + STRIDE + DREAD，中高等級要求 | 不用，但有更好 |
| **需求追溯矩陣 RTM** | 證明安全需求沒被遺漏 | 不用，但有更好 |
| **委外 RFP 資安需求** | 發包時寫需求規格書用 | **不用**，與程式碼無關 |

---

## 怎麼觸發

```
/sec-deliverables
```

或直接說要哪一份：

```
產出附表十查檢表
```

```
幫我做威脅建模，這個系統是高等級
```

```
我要發包，幫我寫 RFP 的資安需求
```

**一次只產一份。** 要多份就分次要求——每份文件的資料來源與判斷邏輯不同，
一次全產容易失焦。

## 產出位置

```
security-deliverables/
├── checklist-appendix10.md          附表十安全查檢表
├── checklist-source.md              源碼安全查檢表
├── security-test-report.md          安全測試報告
├── threat-model.md                  威脅建模
├── rtm.md                           需求追溯矩陣
└── rfp-security-requirements.md     委外 RFP 資安需求
```

與 `sec-audit` 的 `security-audit/` 分開——一個是技術產出，一個是交付文件。

實際範例見 [`examples/`](../../security-compliance-tw/examples/)。

## 最重要的一件事：它不會編造

這些文件會送到稽核人員手上。**編造比留白危險得多**——一個對不上的頁碼、
一個沒有證據的「符合」，會讓整份文件的可信度崩掉。

三條硬規則：

1. **看不到證據的項目不標「符合」**
2. **推導不出來的欄位填「（待填）」**
3. **自動判斷的地方標示信心度**，低信心的寫明依據什麼假設

### 五種判定結果的分界

查檢表的每一項會標成五種之一。最容易混淆的是後兩種：

| 標記 | 條件 |
|---|---|
| 符合 | 有正面證據 |
| 不符合 | 有負面證據 |
| 已修補 | 有修補證據，附位置 |
| **不適用** | **系統不具備該機制**——源碼看得出來「這件事不存在」 |
| **非程式碼可判定** | **要查部署或營運現況**——源碼看不出來 |

分界是「**源碼能不能看出來**」：

- 系統完全沒有登入機制 → 密碼強度、帳號鎖定等項目是**不適用**
  （`grep` 驗證無 session / cookie / 密碼處理，這是源碼看得出來的事實）
- 日誌保存期限、NTP 校時、備份機制 → **非程式碼可判定**（要問維運）

**這兩種都不可以標「符合」。**

### 實測數字給你參考

對一個 41 行的示範程式產出的附表十查檢表（分級中，44 項）：

| 結果 | 項數 |
|---|---|
| 符合 | 1 |
| 不符合 | 9 |
| 不適用 | 15 |
| 非程式碼可判定 | 19 |

**後兩者合計 77%。** 這是小專案的正常現象，但也說明一件事：
**查檢表不是源碼稽核能單獨完成的**，很多項目本來就要人去查營運現況。

## 各文件的重點

### 附表十安全查檢表

依你的分級篩出應查項目——普 33 項、中 44 項、高 55 項。
每項經對照表反查檢查編號，帶入 `findings.md` 的判定結果。

另有一節「**查檢表外的掃描項目**」——例如 HTTP 安全標頭、OS 命令注入。
這些不在查檢表的收錄範圍內，但弱點掃描會標記，不處理一樣過不了驗收。

### 源碼安全查檢表

九大類共 23 項：資料驗證、身分認證、會話管理、授權、密碼學、
錯誤處理、稽核日誌、安全組態、網路架構。

會特別標出「**不適用但會被觸發**」的連動項目。例如「日誌不含機敏資料」
現在不適用（因為沒有日誌），但補上稽核事件後**必然**要記錄使用者輸入，
屆時沒先轉義就會製造日誌注入。**兩項要一起做。**

### 安全測試報告

依 ISO/IEC/IEEE 29119-3 結構，十個章節。

**「範圍」一節一定會寫三條限制**：未執行任何自動化掃描工具、
弱點掃描與滲透測試仍須另行執行、涵蓋範圍限於知識庫已收錄的類別。

不寫這三條，報告會被質疑。**不要把樣式比對的結果寫成「已通過弱點掃描」。**

### 威脅建模

DFD（mermaid 圖，可直接嵌入文件）→ STRIDE 識別威脅 → DREAD 評分 → 對應控制措施。

**DREAD 全部自動打分，但標示信心度**——使用者未必是資安專家，空白表格沒有用；
但假裝每個數字都可靠也是誤導。信心度是有結構的：

| 維度 | 信心 | 為什麼 |
|---|---|---|
| 可重製性 R · 可刺探性 E | **高** | 由漏洞類型與是否需登入決定，程式碼看得出來 |
| 可發現性 Di | 中 | 端點是否公開看得出來，是否已被揭露看不出來 |
| 可能傷害 D · 影響使用者數 A | **低** | 取決於資料敏感度與部署規模，需業務脈絡 |

低信心的欄位照樣填合理預設值，並寫明依據什麼假設、你該去確認什麼。
文件最後有「待人工確認事項」彙整。

> **算法注意**：兩份指引採用不同算法——設計指引的範例採五維相加
> （5–15，12–15 高），流程指引的範例採 `(R+E+Di)×(D+A)`（6–54）。
> 預設採相加法（有明確分級區間），**文件會在表格上方註明採用哪種**，
> 否則對方無法驗算。

### 需求追溯矩陣 RTM

自動化程度最低的一份。六個欄位裡只有兩個推導得出來：

| 欄位 | 能否自動 |
|---|---|
| 高階需求 / 功能需求 | **可** |
| 實作模組 | 部分（有 findings 時可回填） |
| 設計/技術規格 | **不可**，填「（待填）」 |
| 測試案例編號 | **不可**，填「（待填）」 |

**沒有測試案例編號，任何項目都不能標「已測試」**，即使實作已完成。
這是 RTM 最常被打回的原因。

### 委外 RFP 資安需求

**唯一不需要程式碼的一份。** 輸入只有系統分級與系統特性。
不用在專案目錄下執行。

把附表十的控制措施改寫成**可驗收的需求語句**：

> 附表十原文：具有防範 SQL 命令注入攻擊之措施
> 改寫後：廠商應於伺服器端採用參數化查詢或預儲程序，不得以字串串接方式
> 組成 SQL 敘述。驗收時應提供源碼檢測報告佐證。

另有「補充需求」一節，補上查檢表收錄範圍外但實務必要的項目
（API 物件層級授權、AI 提示注入、HTTP 安全標頭等），並標明來源。

## 常見問題

**Q：沒跑 sec-audit 就要查檢表會怎樣？**
它會請你先跑。硬要的話它會自己先跑一次 `sec-audit` 再接下去——實測中
冷啟動測試就是這樣處理的，不會硬編一張標滿「符合」的表。

**Q：文件裡好多「（待填）」，是不是沒做好？**
不是。那些是**確實推導不出來**的欄位——設計文件頁碼、測試案例編號這類
資訊在程式碼裡不存在。填一個看似合理的內容才是問題，稽核時對不上會更難看。

**Q：分級填錯了怎麼辦？**
重跑一次。分級直接決定應查項目數（普 33 / 中 44 / 高 55），差很多。

**Q：可以改文件裡的判定嗎？**
可以，那是給你的草稿。但如果你要把「非程式碼可判定」改成「符合」，
請確定你手上真的有證據——那正是稽核會抽查的地方。
