# 委外開發資安需求（需求規格書用）

| 項目 | 內容 |
|---|---|
| 適用系統分級 | **中** |
| 系統特性 | 對外提供服務、處理個人資料 |
| 依據 | 資通安全責任等級分級辦法附表十 資通系統防護基準 |
| 補充依據 | OWASP Top 10:2021 / 2025、OWASP API Security Top 10:2023 |

**本文件與既有程式碼無關**，係供機關發包時納入需求規格書使用。

## 撰寫原則

每條需求都必須**可驗收**。「應注意安全性」這類無法驗收的敘述不得列入。
每條需求標明驗收方式——附表十各項的查核方式為
**自動化工具檢測**與**人工審查**，兩者皆須，只做其一會被要求補件。

---

## 一、存取控制

1. 廠商應實作使用者會談機制，會談於**閒置至多 30 分鐘**後自動失效，
   且於使用者登出後立即失效。
2. 管理者介面應限制存取來源 IP，或不允許自公開網際網路存取。
3. 廠商應對使用者與角色實施最小權限原則，並提供權限清單之查詢或匯出介面，
   供驗收時審查。
4. 應用程式程序與伺服器服務應以一般使用者權限執行，
   **不得以 root 或系統管理員權限啟動**。
5. 使用者授權檢查應於**伺服端集中實作**，不得僅依賴前端隱藏選項或停用按鈕。

## 二、稽核與可歸責性

6. 系統應記錄下列事件：身分鑑別失敗、存取資源失敗、重要行為、
   重要資料異動、功能錯誤、管理者行為。
7. 稽核紀錄應包含五要素：使用者識別碼（**不得為身分證號等個資型態**）、
   經校時之時間戳記、執行之功能或存取之資源、事件類型或等級、事件描述。
8. 系統應採用單一日誌機制，確保輸出格式一致。
9. 廠商應依稽核紀錄保存需求評估並配置儲存容量，並提出容量計算依據。
10. 稽核處理失效（如容量不足）時，系統應採取明確行動並記錄。
11. 時戳應可對映至 UTC 或 GMT，且系統時鐘應具備定期同步機制。
12. 稽核紀錄應限制存取權限，並定期備份至與原系統不同之實體系統。

## 三、營運持續

13. 重要資料應定時同步至備份或備援環境，備份資料應限制存取。

## 四、識別與鑑別

14. 使用者密碼長度應為 **12 字元以上**，並包含英文大小寫、數字及特殊字元。
15. 系統應要求定期更換密碼，新密碼**不得與前 3 次使用過之密碼相同**。
16. 身分鑑別失敗達 **5 次**後，應鎖定該帳號**及來源 IP 至少 15 分鐘**。
17. 身分鑑別相關資訊不得以明文傳輸。
18. 身分鑑別及重要交易行為應採用圖形驗證碼或同等之人機辨識機制。
19. 密碼重設應於重新確認身分後，發送**一次性且具時效性之令牌**，
    驗證令牌有效性後方允許重設。不得直接寄送新密碼。
20. 密碼輸入欄位應遮蔽顯示內容。
21. 使用者密碼應加入隨機亂數（Salt）後，以金鑰推導函式處理再儲存。
    **應採用 bcrypt、scrypt、Argon2 或 PBKDF2，不得以 MD5、SHA-1、
    SHA-256 直接雜湊。**

## 五、系統與服務獲得

22. 廠商應於需求階段以檢核表方式確認系統安全需求，並提出檢核結果。
23. 廠商應於設計階段識別可能影響系統之威脅，執行風險分析與評估，
    並將結果回饋需求階段修正安全需求。
24. 系統應於伺服端具備防範 **SQL 命令注入**之措施，
    應採用參數化查詢或預儲程序，**不得以字串串接方式組成 SQL 敘述**。
25. 系統應具備防範**跨站腳本攻擊**之措施，
    應使用具自動跳脫功能之樣板引擎，**不得以黑名單過濾特殊字元作為唯一防護**。
26. 系統應具備防範**跨站請求偽造**之措施。
27. 發生錯誤時，使用者頁面僅顯示簡短錯誤訊息及代碼，
    **不得包含堆疊追蹤、SQL 錯誤原文或系統路徑**。
28. 所有功能皆應進行錯誤及例外處理，並確保資源正確釋放。
29. 廠商應於交付前執行**弱點掃描**，並提出掃描報告與修補紀錄。
30. 部署環境之作業平台應定期更新，並關閉不必要之服務及埠口。
31. 廠商應表列系統依賴之外部元件與版本，關注其安全漏洞通告並定期評估更新。
32. 系統依賴之外部元件不得使用預設或空白密碼。
33. 開發、測試與正式作業環境應作區隔。
34. 廠商應交付系統發展生命週期各階段之相關文件並納入版本管理。

## 六、系統與通訊保護

35. 機敏資料傳輸時應採用加密機制。
    **本系統處理個人資料，全站應採用 HTTPS**，不得有任何明文傳輸路徑。

## 七、系統與資訊完整性

36. 發現系統有被入侵跡象時，應通報機關指定人員。
37. 廠商應提供監控機制，以偵測攻擊與未授權連線。
38. 系統應於**伺服端**檢查使用者輸入資料之合法性，
    採用白名單方式驗證格式、長度與範圍。

## 八、缺口補充需求

> 以下項目**非屬附表十查檢表所列**，係依 OWASP Top 10 與相關標準補充。
> 建議納入以降低驗收時弱點掃描不通過之風險——這些項目掃描器一定會標記，
> 但查檢表上找不到對應條目，容易在發包時被遺漏。

### 對外服務相關

39. 系統回應應設定下列 HTTP 安全標頭：
    `Content-Security-Policy`、`Strict-Transport-Security`、
    `X-Content-Type-Options`、`X-Frame-Options`、
    `Referrer-Policy`、`Permissions-Policy`。
    **CSP 應完整定義 `default-src`、`object-src`、`frame-ancestors`、`base-uri`**
    ——僅部分實作會使掃描工具基於保守假設判定為高風險。
40. Cookie 應設定 `Secure`、`HttpOnly`、`SameSite` 屬性。
41. 應停用 TLS 1.1 以下版本，並明列允許之加密套件，
    **不得使用 `ALL`、`HIGH` 等集合名稱**。
42. 系統不得於回應中洩漏版本資訊（`Server`、`X-Powered-By` 標頭）
    或開啟目錄列表；部署時不得殘留 `.git`、`.env`、備份檔。
43. 回傳非 HTML 內容時應設定正確之 `Content-Type`，
    避免瀏覽器型別猜測造成儲存型跨站腳本攻擊。

### 個資處理相關

44. 稽核紀錄中不得包含密碼、令牌、身分證號、信用卡號等敏感資訊。
45. 寫入日誌之外部輸入應先行轉義換行與控制字元，避免日誌偽造。

## 九、交付項目

廠商應於各階段交付下列項目。**未列為交付項目者，廠商通常不會執行。**

| 階段 | 交付項目 |
|---|---|
| 需求 | 安全需求檢核表、需求追溯矩陣（RTM）初版 |
| 設計 | 威脅建模結果（資料流程圖、威脅清單、風險評分）、威脅與控制措施對應表 |
| 開發 | 源碼安全查檢表檢核結果 |
| 測試 | 源碼檢測報告、弱點掃描報告、誤判判定佐證、更新後之 RTM |
| 部署維運 | 部署環境強化程序、變更管理程序、監控量測程序、事故處理程序 |

## 待人工確認事項

1. **系統分級**——本文件以「中」撰寫。核定為「高」時，另需納入
   多重因素身分鑑別、來源 IP 白名單、高可用性架構、滲透測試、
   機敏資料靜態加密、重要紀錄雜湊值、通信流量自動化監控、
   稽核失效即時告警等項目，且第 35 項應加嚴為使用國際機構驗證之演算法。
2. **個資範圍**——第 44 項所列之敏感欄位需依實際蒐集項目調整。
3. **是否含 API 或 AI 功能**——本文件依「無 API 端點、無 AI 功能」撰寫。
   若系統包含 REST / GraphQL API，需另補物件層級授權、屬性層級授權、
   功能層級授權與資源消耗限制等需求；若包含 LLM 功能，
   需另補提示注入防護、模型輸出處理與系統提示保護等需求。
