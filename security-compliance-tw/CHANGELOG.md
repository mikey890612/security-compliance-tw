# 更新紀錄

版本號以 `.claude-plugin/plugin.json` 為準。已安裝的版本看
`~/.security-compliance-tw/plugin/.claude-plugin/plugin.json`；
專案裡由 `sec-harden` 產生的規則檔，版本寫在標記區塊的第一行。

- **patch**（0.2.**x**）：修正文字、數字、連結，判定結果不變
- **minor**（0.**x**.0）：新增或更正 check、掃描器對照、skill 的流程——判定結果可能改變，建議更新
- **major**（**x**.0.0）：check-id 異動或移除——舊的 `findings.md`、`false-positives.md` 可能對不上

## 0.4.0（2026-09-24）

**建議更新**：`sec-audit` 載入的 check 變多——普級、無個資或內部系統的專案，
`findings.md` 會多出之前整類漏查的項目；另新增 5 則 check。

- 載入規則改由分級欄推導。`sast-authz`、`sast-logging`、`dast-tls-cookie`、`dast-info-leak`
  改為**一律載入**：這四檔都含普級必查的項目，之前只在中級、有個資或對外服務時才載入
- `sast-crypto` 另在將面對 SAST 時載入；`dast-headers` 改為分級 ≥ 中、對外服務或將面對弱點掃描時載入。
  第 3 題答「不知道」視為各類掃描器都會面對
- 新增「逐則決定要不要查」：本分級沒要求、但使用者將面對的掃描器會標的 check 照樣查；
  兩者皆否才歸不適用
- `mapping.md` 的分級欄一律照附表十原文，刪除「刻意放寬分級之處」：`SAST-CRYPTO-001` 回到只有高、
  `SAST-LLM-003` 回到中高。該節與主表不一致，會讓 `SAST-LLM-002`（LLM 輸出造成的 SQL 注入）
  被排成 P1；P0 規則的例外子句一併刪除
- 驗證器新增三項交叉檢查：分級欄不得比附表十寬、載入表與分級欄一致、
  `sec-audit` 涵蓋範圍表與載入表一致
- 新增 5 則 check（90 → 95）：`SAST-INJ-005` XML 外部實體、`SAST-INJ-006` 不安全的反序列化、
  `SAST-INJ-007` HTTP 標頭注入、`SAST-REDIRECT-001` Open Redirect，以及新檔 `sast-dependencies.md` 的
  `SAST-DEP-001` 已知漏洞元件（附表十 4.5.5，普中高必查，一律載入）
- 新 check 的開源對照在新 fixture `testdata/sample-untrusted-data/` 實跑，12 列標 `verified`。
  實測發現 lxml 的 `resolve_entities=True`（真正會解析外部實體）bandit 與 semgrep 都不標，
  它們反而標新版 Python 已安全的 `xml.etree`——判定準則照實際解析器設定寫
- `SAST-DEP-001` 不憑記憶判定版本漏洞：模式 1 只盤點元件，`findings.md` 開頭新增「待使用者執行」，
  列出 `npm audit`／`pip-audit`／`govulncheck` 指令，使用者提供輸出後再判定
- 依第五次盲測修正：`4.5.3.4`（HTTP 安全標頭）在 `mapping.md` 標「（內文）」——查檢表沒有這一列，
  不觸發 P0 第 ① 條，勾稽表也比照查檢表外；前端顯示的錯誤只來自瀏覽器 API 時改判改寫即過；
  Go 只漏 panic 路徑的資源釋放改判改寫即過；`DAST-HDR-002` 涵蓋內網 HTTPS；
  TLS 在 repo 以外終結時列「待使用者執行」

## 0.3.0（2026-09-24）

**建議更新**：`sec-audit` 的判定分類與優先序改變，`findings.md` 的排序會不同。

- 判定固定為四類：**真漏洞／改寫即過／誤判／不適用**。新增的「改寫即過」收納
  「實質安全、但寫法會被標」的項目（例如 `_ = f.Close()`、非安全用途的 md5），
  排 P2，不再和真漏洞擠在一起
- 優先序改排「不修會不會被驗收退件」：P0＝真漏洞，且查檢表必查（本分級標 ◎）或
  掃描器確定會標 Critical／High；P1＝其他真漏洞；P2＝改寫即過。
  **沒有授權檢查這類掃描器不會標的真漏洞照樣排 P0**，不再列為「表外」。
  知識庫裡未校準的掃描器等級（`unverified`）不再拿來排序
- check 檔的判定用詞統一：「真問題」「真缺口」改為「真漏洞」，「可接受」依語意改為
  「通過」（20 處）、「不適用」或「誤判」（各 1 處）
- 查檢表模板：判定為「誤判」或「改寫即過」的 check 視為通過，改寫即過要在佐證欄註明
- 載入規則：程式碼看得出來的特性以較寬的一方為準（例如使用者沒勾 API，但有回 JSON 的端點就載入
  `sast-api-authz`，並在 findings 開頭寫明）；面對商用 SAST 一律載入 `dast-tls-cookie`（Cookie 屬性
  寫在原始碼裡）；技術棧也看實際存在的原始檔；登入判定不再把 CSRF token 這類 cookie 算進去
- 預設掃描由第三方執行：註冊 cleanse rule、調規則這類需要改掃描設定的處置一律標「選配」，
  主路徑改為程式碼照改、仍被標就走誤判佐證（附實際輸出樣本）
- P0 的「查檢表必查」以附表十原文分級為準——`mapping.md` 為了載入而刻意放寬的分級不算
- SAST-AUTHZ-001：完全沒有身分鑑別的系統同樣歸本則；第三方套件的發現如何歸入四類寫進 `sec-audit`
- 「已知風險接受」（例如對方系統只收 MD5）明定為真漏洞的一種處置，記在 `false-positives.md` 的獨立段落，
  不與誤判混在一起；第三方套件的發現若風險已被消除，直接判誤判
- 修補若會新增機制（例如補上登入），修完要重跑模式 1

維護者：驗證器擋下 check 檔中的舊判定用詞。

## 0.2.0（2026-09-24）

**建議更新**：`sec-audit` 判讀 Fortify 報告的結果會不同。

- `sec-audit`：Fortify 對照依一份真實專案的報告校準。檔案上傳的規則名更正為
  `Often Misused: File Upload`——**舊版會把這類發現誤報成「本知識庫尚未涵蓋」**。
  等級改用實測值，多數比舊版低
- `sec-audit` 模式 2：依規則名稱分組判讀、用含子類別的全名反查、優先序以報告上的等級為準、
  第三方套件（`vendor/`）的發現另行處置
- `sec-audit`：誤判的判定從「三要件同時成立」改為兩點——**風險已被消除**（來源不可控、
  路徑上有消毒、或控制存在於工具看不到的地方，三者任一）＋**有具體佐證**。舊寫法連
  「來源是常數」「框架自動跳脫」這類 check 本身判為誤判的情況也擋下，不同次執行的判斷會不一致
- `sec-harden`：寫 Android／iOS 程式時會觸發；行動端先用速查，速查沒涵蓋的情境才讀完整 check
- 專案規則檔（`AGENTS.md`、Cursor `.mdc` 等）的標記帶版本號，可比對專案是否需要重裝
- 新增 `./install.sh --check [專案目錄]`：比對已安裝、本機 clone、GitHub 的版本，列出各版變更；安裝超過 30 天沒檢查時，三支 skill 會在回覆開頭提醒一句
- 三支 skill 找不到知識庫時會停下來，請使用者執行 `install.sh`，不再憑印象作答
- 修正安裝後會失效的文件連結，以及多處過期的則數與條數

維護者：`tools/validate_kb.py` 新增文件數字、路徑、check 檔登錄、ROOT 段落、
版本與本檔的一致性檢查；新增 `testdata/sample-go-web` 與盲測紀錄
（`testdata/blind-tests/`：模式 1 預判命中 2／8 → 8／8）；CI。
