> 本檔為繁體中文摘要改寫，非逐字翻譯；授權全文見 plugin 根目錄的 `THIRD_PARTY_NOTICES.md`。

本知識庫其他部分回答的是「**掃描器會不會標、驗收會不會退件**」。
本檔回答另一個問題：「**這份程式碼有沒有真的能被利用、跨越信任邊界的漏洞**」。
兩者互補，不互相取代：

| | `sec-audit` 模式 1／2 | 深度稽核（本檔） |
|---|---|---|
| 依據 | `checks/*.md` 的壞味道、掃描器規則 | 信任邊界與不變量（invariant），逐條追原始碼 |
| 判定 | 真漏洞／改寫即過／誤判／不適用 | `confirmed`／`needs_validation`／`rejected` |
| 缺少最佳實務（例如沒設某個標頭） | 掃描器會標就要處理 | 單獨不算發現，只列為強化建議 |
| 產出 | `findings.md`、`false-positives.md` | `findings.json`、覆蓋帳本、三份報告 |
| 適合 | 送掃、驗收、交付文件 | 上線前的高風險系統、委外程式碼複審、事件後的根因調查 |

**不要把兩套判定混在同一份表。** 深度稽核的結果要進驗收文件時，依下方「換算回四類」處理。

## 兩種使用方式

**預設只當指引用。** 載入本檔不代表要跑完整流程，也不代表可以寫檔。

- **指引模式**——使用者問資安問題、要針對某段程式碼做聚焦審查、要判讀某個發現：
  只取本檔與 `deep-audit-hunting.md`、`deep-audit-ai.md` 中相關的部分回答。
  不建立輸出目錄、不寫稽核檔案
- **完整稽核模式**——使用者**明確要求**稽核／滲透測試整個 codebase、要求完整或端對端審查、
  或要求產出報告檔案時，才依序跑完下方六個階段並寫出產出檔

請求可能屬於任一種時，**先問一個聚焦的問題**再動手。

兩種模式都受 `deep-audit-safety.md` 的執行安全規則約束。

## 核心原則

1. **要有邊界、也要有結果。** 每個候選都要講清楚：較低信任的主體（principal）是誰、
   它送進什麼輸入或動作、原本該擋下它的控制在哪、跨越了哪條邊界、影響到哪個主體或資源、
   觀察到（或擁有者可觀察到）的具體結果。缺任一項就不是確認的發現
2. **用有界的本機證據。** 靜態閱讀確立路徑；行為問題用最小的本機檢查解決——
   既有單元測試、最小 harness、小型 fixture、假租戶的整合測試、本機渲染的設定。
   觀察到錯誤的回傳值、越權讀到假資料等**最小效果就停**，不延伸成持久化或擴大影響
3. **尊重原始碼的可見範圍。** 代理、雲端供應商設定、瀏覽器標頭、身分政策、網路拓樸都是真實的控制。
   repo 裡看不到時，**不假設有、也不假設沒有**——列為 `needs_validation`，寫清楚缺的是哪個事實
4. **優先度與確定性分開。** 只有 `confirmed` 有嚴重度；`needs_validation` 不給嚴重度，
   它不是「信心較低的漏洞」，而是「卡在特定事實上的、有原始碼依據的假設」
5. **建議最小有效修法。** 找出程式碼必須守住的不變量，在最後一個可信的決策點用最窄的修改守住它，
   附回歸測試案例。稽核只描述修法，**不改目標原始碼**

### 從具體的不變量出發（每個獵洞者都照這六步）

1. 指出較低信任的主體與它一開始的能力
2. 指出被接受的值、動作、狀態轉換或資源選擇器
3. 找出應該拒絕、綁定、隔離、限制或撤銷它的控制
4. 追那個決策**之後**的確切原始碼路徑
5. 停在最小的受影響假資料、錯誤回傳值或可在本機觀察的效果
6. 寫出能守住不變量的原始碼修改與回歸案例

**深度界線**：只追能到達被指派邊界、或該邊界所依賴的路徑；不變量確定（成立或不成立）就停，記錄結果。

**一定要試的「難走的路」**：缺值、空值、零、負數、最大值、超限、重複、混合編碼、過期、已撤銷、
順序顛倒、並行、遷移到一半、相依失敗、回滾——只試介面真的接受的。
每個解析器或政策交接點都比對正規化方式與單位是否一致。
同一效果的兄弟路徑（舊版、批次、重試、取消、遷移、錯誤處理）要比的是**控制是否等價**，不只是有沒有。

## 三種判定與證據要件

| 判定 | 意思 | 必備 | 不得出現 |
|---|---|---|---|
| `confirmed`（已確認） | 有完整原始碼追蹤、有界本機觀察結果、跨邊界的實質影響 | 根因、預期行為、依序的 trace、證據、條件、目標中立的重現方式、修法、嚴重度、信心 | 阻礙清單、驗證計畫、排除理由 |
| `needs_validation`（待驗證） | 有原始碼依據的邊界假設，但決定性的事實不在 repo 也無法在本機觀察 | 宣稱的根因、trace、證據、**具體阻礙**、至少一個驗證計畫（本機 fixture 或請擁有者觀察的部署事實） | 嚴重度、重現方式、修法 |
| `rejected`（已排除） | 被原始碼、本機行為、可見的控制、無實質影響或不可能的前提推翻 | 宣稱的根因、trace、證據、排除理由 | 嚴重度、重現方式、修法 |

- `needs_validation` **不是**放臆測的地方；被原始碼推翻的候選要判 `rejected`，不是待驗證
- `rejected` 要保留，下次稽核才不會在證據未變時重複提出同一個主張
- trace 有多步時，第一步是 entrypoint、最後一步是 sink，中間是 propagation
- 同一根因在所有狀態下用**同一個指紋**（fingerprint）；指紋由原始碼推導，
  不含行號、波次、代理、嚴重度或判定
- 證據路徑一律用 repo 相對路徑，不用絕對路徑

### 嚴重度錨點（只給 `confirmed`）

- **critical**——未經驗證的攻擊者取得程式碼執行、完整資料庫存取，或可接管任意帳號
- **high**——完全擊破一個明確的安全控制且有實質後果：驗證繞過、跨租戶讀寫、
  影響其他使用者的儲存型腳本執行、已驗證的程式碼執行、未經驗證即可遠端停掉共用服務
- **medium**——真實的邊界違反，但影響範圍有限、前提少見或後果侷限於少數資源
- **low**——揭露非機密的內部資訊，或要持續投入才有極小收穫
- **informational**——已確認但影響極小，主要作為更大發現的前提

區分 high 與 medium：展示出的結果是「**完全擊破**」一個有實質後果的明確控制，還是只是「**削弱**」它？
講不出具體損害，嚴重度就比感覺的低。整體嚴重度不得高於已展示的影響。

## 完整稽核的六個階段

### 事前設定

- **目標**：受審 repo 的絕對路徑；**來源版本**：受審的 commit，以及工作樹是否有未提交變更
- **輸出目錄**：預設放在**目標 repo 之外**（例如 `~/security-audit-runs/<repo>/run-<N>/`）。
  稽核產出含未修補的漏洞細節，**不得進版控、不得放進公開 repo**。
  只有使用者明確指定、且確認整個目錄已被 `.gitignore` 涵蓋時，才可放在目標內
- **執行設定檔**：`quick`（小目標或重跑：一波獵洞加一次覆蓋檢查，每個候選一位驗證者）、
  `standard`（預設）、`deep`（高風險或大型目標：依子系統與生命週期細分、覆蓋檢查跑到乾淨為止、
  候選驗證與最終複核分由不同代理）。**設定檔只改廣度與重複度，不降低證據門檻**
- **範圍稽核**：只審指定路徑、子系統或兩個版本間的差異時，範圍外的部分記為 `out_of_scope`，
  **不可**記為 `covered`；`quick` 或範圍稽核的報告必須自稱「部分覆蓋」
- **預算**：使用者設了代理呼叫上限時，先保留覆蓋檢查與驗證的額度，再分配獵洞者；
  預算不夠就說，提議縮小範圍或改用 `quick`，**不要默默降低證據要求**

**寫入隔離**：協調者（parent）是共用檔案（`run-metadata.json`、`architecture.md`、
`coverage-ledger.json`、`findings.json` 與三份報告）的唯一寫入者。每個獵洞者或驗證者只能寫自己的
`agents/<agent-id>/scratch/`，不能改共用檔、目標原始碼或其他代理的目錄。

### 階段 1：偵察與覆蓋帳本

平行派出唯讀的研究代理，各回傳附 `檔案:行號` 的事實，不寫檔：

| 代理 | 要回答的問題 |
|---|---|
| 1a 產品與技術棧 | 產品類型與使用者、語言框架與建置方式、進入點與子系統邊界、可離線執行的建置與測試指令（偵察時不執行） |
| 1b 主體與控制 | 每個較低信任主體與其設計上的權限、各入口的身分鑑別、逐資源授權與租戶範圍、權限變更／撤銷／復原路徑、哪些控制在 repo 裡看得到、哪些依賴部署事實 |
| 1c 輸入面與 sink | 所有外部輸入進入點（HTTP、RPC／訊息、檔案／壓縮檔、CLI／環境變數／設定、外掛／相依／CI、雲端事件、模型脈絡／工具參數、行動 deep link／WebView、本機 IPC），追主要轉換、衍生副本與資安相關的 sink |
| 1d 本機執行與部署可見度 | 可在沙箱內用假資料驗證的既有測試、會抓相依或碰共用狀態而**本次禁止**的指令、repo 看不到而需列待驗證的部署控制、本機平台能否落實 `deep-audit-safety.md` 的全部控制 |

協調者據此寫 `architecture.md`，並建立**覆蓋帳本** `coverage-ledger.json`：
每個「輸入面 × 信任邊界 × 子系統 × 攻擊類別」的實質組合是一個單元。每個單元記錄：

- `coverage_id` 與 `canonical_refs`：由原始碼物件推導的穩定識別（例如 `src/router.go#POST /users/:id`），
  跨次稽核同一物件用同一個識別；不含波次、代理、判定、行號
- `starting_paths`、選用與排除的攻擊類別區塊（排除要附理由）
- `status`：`planned`／`in_progress`／`covered`／`candidate`／`blocked`／`deferred`／`not_applicable`／`out_of_scope`
- `agent_id`、`reviewed_paths`、`local_checks`、`result_fingerprints`、`unresolved`

狀態與欄位要一致：`covered` 必須有負責人與非空的已審路徑與檢查、不得有未決事項；
`candidate` 才可以帶指紋；`blocked` 要有部分證據與具體阻礙；`deferred`／`out_of_scope` 要有理由。
**帳本就是覆蓋宣稱**——架構摘要、代理數量或「授權已審」這類句子都不是覆蓋證據。

有前次稽核紀錄時，先讀前次的帳本與 `findings.json`：原始碼未變的 `confirmed` 可沿用但仍要走本次驗證；
原始碼變了的要重新驗證；前次的 `needs_validation`、`deferred`、`blocked` 一律是本次的工作。
沒有前次紀錄就在報告中說明。**不要暗示一次稽核就窮盡目標。**

### 階段 2：依帳本分波獵洞

- 協調者把 `planned` 單元分給互相隔離的獵洞者，**不把不相關的邊界合併給同一人**。
  預算不夠時依序優先：未驗證／最低信任的入口 → 保護最有價值資源（憑證、跨租戶資料、程式碼執行、發布權）的邊界 →
  前次缺口與變更過的原始碼 → 此類目標歷來常出確認發現的攻擊類別；同分依 `coverage_id` 字典序
- 獵洞者的提示要包含：`architecture.md` 原文、指派的單元、**選用的攻擊類別區塊原文**（不能只給名稱）、
  排除的區塊與理由、上方「從具體的不變量出發」、下方候選門檻、本機執行邊界、不可重複的同儕單元
- 獵洞者只回傳**一個結構化結果**：每個單元的處置（`covered`／`candidate`／`blocked`）、
  已審路徑、檢查紀錄、候選清單、強化建議（非發現）、以及 `uncovered`（發現的新邊界，由協調者建新單元）
- 發現高或嚴重等級的可重用根因時，在自己負責的單元內找詞彙、結構與邏輯上的變體；
  同一根因合併，但每個變體的條件與影響要各自確立

**候選門檻**（獵洞者回傳前自我檢查）：

1. 候選要有完整的 repo 相對 trace，以及根因證據——包括 repo 裡看得到的**最強控制**
2. 擬判 `confirmed` 者要有有界的本機觀察結果、跨邊界的實質影響、完整條件，且沒有看得到的阻擋層
3. 不把當機升格成程式碼執行、一般工作量升格成共用服務癱瘓、同一主體的動作升格成提權
4. 必要事實在 repo 裡看不到、本機也觀察不到 → `needs_validation`，寫明阻礙，不給嚴重度
5. 沒有受影響主體或資源的「缺少最佳實務」→ 排除或列強化建議，不是發現
6. 沒有東西通過門檻時，回傳空的候選清單

**覆蓋檢查者（coverage critic）**：每波獵洞後派一位全新的唯讀代理，只檢查覆蓋、不找漏洞——
沒對應到單元的入口、沒查的平行路徑、漏掉的生命週期模式、選了攻擊類別卻沒有單元、理由不成立的排除、
沒有路徑或檢查就結案的單元、前次待驗證項沒有人處理。它提出的缺口由協調者建單元，進下一波。
`standard`／`deep` 一直跑到覆蓋檢查者回報乾淨為止；`quick` 只跑一次，提出的缺口記為 `deferred`。

### 階段 3：獨立驗證每個候選

- 依指紋與根因合併候選後，每個候選交給**沒有參與獵洞的全新驗證者**
- 驗證者重讀每個引用的原始碼位置，能安全重現的決定性檢查要自己再跑一次；
  **不得收到其他驗證者的結論**
- 驗證者可以把 `needs_validation` 升為 `confirmed`（自己確立完整路徑與觀察結果後）、
  把擬確認者降為 `needs_validation`（仍有特定部署或執行期事實未知）、或判 `rejected`
- 格式錯誤或夾帶散文的驗證結果**直接作廢、不修補**，換一位新的驗證者重跑

### 階段 4：寫出並驗證 `findings.json`

協調者把所有經獨立判定的紀錄依指紋排序寫入 `findings.json`，三種判定各用自己的欄位（見上表）。
JSON 的欄位名與判定值沿用上游英文（`confirmed` 等），以便直接用上游的 `report-schema.json` 與驗證腳本檢查：

```sh
node <上游 skill 目錄>/validate-findings.cjs <輸出目錄>/findings.json
node <上游 skill 目錄>/validate-coverage-ledger.cjs <輸出目錄>/coverage-ledger.json
```

本知識庫**不隨附**這兩支腳本與 schema（避免另外維護一套 Node 工具鏈），
需要時從上游 repo 的 `skills/security-audit/` 取得，建議釘選上方標示的 commit。
驗證通過只代表格式與帳本一致，不代表結論正確。

### 階段 5：以全新視角複核最終紀錄

每筆 `confirmed` 與 `needs_validation` 各派一位全新的唯讀複核者，核對的是**結構化紀錄本身**，不是獵洞者的說明：

- `confirmed`：每個 trace／證據的路徑與行號、真實的入口與輸入形狀、每個條件與可見的阻擋層、
  受影響主體與已展示的影響、嚴重度沒有高過影響、修法是否真的守住不變量而不是把信任搬到別處
- `needs_validation`：原始碼路徑真實且只支持所宣稱的根因、每個阻礙都是決定性且本機確實答不出來、
  講得出邊界與可能的具體結果、驗證計畫具體可行（**不得**是對部署環境發送稽核流量）

複核者若把紀錄升為更強的判定，或實質改變根因、trace、重現方式、影響或嚴重度，
這份替換紀錄要再交給**另一位**從未經手的驗證者確認後才生效。`quick` 可把階段 3 與 5 合併，
但**任何設定檔都不能省略對 `confirmed` 的獨立複核**。

### 階段 6：從最終紀錄產出目標中立的報告

只在每筆紀錄都通過階段 5 之後才寫報告；報告文字**不得改變**任何判定、嚴重度、阻礙或影響。

- `REPORT.md`：設定檔、範圍、預算、來源版本、「僅原始碼與本機沙箱執行」聲明、前次紀錄使用情形、
  延後與範圍外的覆蓋；整體資安體質摘要；確認發現表（嚴重度、標題、邊界、一句話結果）；
  每個確認發現的位置、主體、有界重現、條件、影響與最小修法；獨立的待驗證表（不給嚴重度）；
  強化建議與良好寫法；依帳本的覆蓋統計
- `FINDINGS-DETAIL.md`：每個 medium 以上確認發現的完整 trace、假主體與假資源、原生介面的輸入、
  觀察結果與它證明的不變量、修法與回歸案例
- `NEEDS-VALIDATION.md`：每個待驗證項的 trace、已驗證的證據、具體阻礙、可行的本機或擁有者觀察計畫

「目標中立」的意思：用目標**原生的介面**描述重現——函式庫用函式呼叫、解析器用 fixture、CLI 用指令、
基礎設施用本機渲染的政策；**不寫成對線上系統的攻擊步驟**。乾淨的稽核可以零個確認發現，
照實寫出結果與剩餘限制，不要為了湊數產生 low 發現。

**結束條件只有兩種**：(a) 六個階段的產出都寫完且驗證通過；
(b) 在 `run-metadata.json` 記下 `run_status: "incomplete"` 與確切原因，並在報告中揭露缺口。不可停在階段中間。

## 換算回四類（要進驗收文件時）

深度稽核的結果要寫進 `findings.md` 或交給 `sec-deliverables` 時：

| 深度稽核 | `findings.md` | 說明 |
|---|---|---|
| `confirmed` | **真漏洞** | 優先序依 `profile.md` 的「優先序」排；嚴重度另附在處置欄。有對應 check 時寫 check-id，沒有就寫「深度稽核發現（知識庫無對應 check）」 |
| `needs_validation` | **待使用者執行** | 附阻礙與擁有者要提供的設定或觀察；提供後再判定 |
| `rejected` | 不列 | 若掃描器仍會標同一處，另依 `sec-audit` 的誤判準則處理，佐證寫進 `false-positives.md` |
| 強化建議 | 不列為發現 | **但**若某則 check 的掃描器會標（例如缺安全標頭），仍照該 check 的判定準則處理——驗收看的是掃描結果 |

附表十或 OWASP 編號一律查 `mapping.md`，不在深度稽核的紀錄裡自行編號。

## 反模式

1. 把清單上的偏差當成漏洞
2. 沒有可到達的邊界違反，只是縱深防禦建議
3. 本機證據足夠時，卻跑去打線上或共用環境
4. 猜測 repo 裡看不到的供應商、代理、瀏覽器、身分或部署行為
5. 把同一主體本來就有的權限、或只影響自己的行為，當成跨邊界結果
6. 回報的解析器或執行期效果比實際觀察到的更強
7. 獵洞結果只有散文，無法去重或驗證
8. 重複回報沿用的前次確認紀錄，或拿它當範例讓獵洞先入為主
9. 給 `needs_validation` 嚴重度
10. 獨立複核前就寫報告，或報告文字與 JSON 不一致
