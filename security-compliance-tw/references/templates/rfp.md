# 委外 RFP 資安需求產出規則

依 103 年《安全軟體發展流程指引》3.6 與《Web 應用程式安全參考指引》4.5.6。

**這份文件與專案程式碼無關。** 它是機關發包前寫需求規格書用的，
輸入只有「系統分級」與「系統特性」。不需要 `findings.md`，
也不需要在專案目錄下執行。

## 產出步驟

1. 詢問：系統分級（普/中/高）、是否對外服務、是否有 API、
   是否有 AI 功能、是否處理個資或金流
2. 讀 `../controls-appendix10.md`，取該分級標 ◎ 的全部項目
3. 依系統特性補上實務必要的補充項目（見下方「補充需求」）
4. 每項改寫為**可驗收的需求語句**
5. 加上交付項目與驗收方式

## 需求語句的寫法

附表十的原文是控制措施描述，不是需求語句。要改寫成可驗收的形式。

| 附表十原文 | 改寫為需求語句 |
|---|---|
| 具有防範 SQL 命令注入攻擊之措施 | 廠商應於伺服器端採用參數化查詢或預儲程序，不得以字串串接方式組成 SQL 敘述。驗收時應提供源碼檢測報告佐證。 |
| 密碼添加亂數(Salt)進行雜湊處理後儲存 | 廠商應採用 bcrypt、scrypt、Argon2 或 PBKDF2 等金鑰推導函式儲存使用者密碼，不得以 MD5、SHA-1、SHA-256 直接雜湊。 |

**每條需求都要能被驗收。** 寫「應注意安全性」這種無法驗收的句子等於沒寫。

## 必須納入的交付項目

依流程指引 3.6.2，把安全活動的產出列為交付項目，否則廠商不會做：

| 階段 | 交付項目 |
|---|---|
| 設計 | 威脅建模結果與控制措施對應表、安全特點檢視結果 |
| 開發 | 源碼安全查檢表檢核結果 |
| 測試 | 源碼檢測報告、弱點掃描報告、（高等級）滲透測試報告 |
| 部署維運 | 部署環境強化程序、變更管理程序、事故處理程序 |

## 補充需求

查檢表收錄範圍外、但現代系統實務必要的項目。依系統特性選入：

**有 API 端點時**：
- 廠商應確保每一筆資料存取皆驗證呼叫者對該筆資料的擁有權，
  不得僅以路徑參數或查詢參數之識別碼直接查詢
- 廠商應明確列舉 API 回應欄位，不得直接序列化資料模型
- 廠商應對請求繫結採用白名單，防止大量賦值
- 廠商應對查詢筆數、請求頻率、上傳大小設定上限

**有 AI 功能時**：
- 廠商應將系統指令與使用者資料分離，外部取得之內容須明確標記為資料
- 廠商應將模型輸出視為不可信輸入，經驗證後方可用於查詢、命令或頁面輸出
- 系統提示不得包含金鑰、內部位址或授權規則

**對外服務時**：
- 廠商應設定 Content-Security-Policy、Strict-Transport-Security、
  X-Content-Type-Options、X-Frame-Options、Referrer-Policy、
  Permissions-Policy 等回應標頭
- Cookie 應設定 Secure、HttpOnly、SameSite 屬性

**這一節要標明來源**：「以下項目係依 OWASP API Security Top 10 與
OWASP Top 10 for LLM Applications 補充，建議納入以降低驗收時
弱點掃描不通過之風險。」

## 驗收方式

每條需求標明驗收方式，對應附表十的查核方式欄：

- **自動化工具檢測**——源碼檢測或弱點掃描報告佐證
- **人工審查**——設計文件、查檢表、程式碼審查紀錄佐證

附表十的項目**兩者皆須**。只做其一在驗收時會被要求補件。
