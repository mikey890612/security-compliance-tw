# 威脅建模產出規則

方法依據 103 年《安全軟體設計參考指引》第 3.4 節。
流程：資料流程圖 → STRIDE 識別威脅 → DREAD 評分排序 → 對應控制措施。

## 步驟 1：建立資料流程圖（DFD）

從程式碼推導，五種元素：

| 元素 | 程式碼中對應什麼 |
|---|---|
| 外部實體 | 使用者、第三方系統、外部 API 的呼叫方 |
| 程序 | handler、service、背景工作、排程 |
| 資料流 | HTTP 請求與回應、函式呼叫、訊息佇列 |
| 資料儲存庫 | 資料庫、檔案、快取、物件儲存 |
| 信任邊界 | 網路邊界、程序邊界、權限切換處 |

推導來源：路由註冊、資料庫連線、外部 HTTP client、檔案存取、環境變數。

**信任邊界最重要**——它決定哪些資料流需要驗證。至少標出：
網際網路 ↔ 應用程式、應用程式 ↔ 資料庫、應用程式 ↔ 第三方服務。

輸出格式用 mermaid，稽核文件可直接嵌入：

```mermaid
flowchart LR
  U[使用者] -->|HTTPS 請求| API[API 服務]
  API -->|SQL| DB[(資料庫)]
  subgraph 信任邊界：內部網路
    API
    DB
  end
```

## 步驟 2：STRIDE 識別威脅

各元素可能發生的威脅類型不同，只針對可能的組合列威脅：

| | 偽冒 S | 竄改 T | 否認 R | 資訊洩漏 I | 阻斷服務 D | 權限提升 E |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| 外部實體 | ✓ | | ✓ | | | |
| 程序 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 資料流 | | ✓ | | ✓ | ✓ | |
| 資料儲存庫 | | ✓ | ✓ | ✓ | ✓ | |

對應的安全特性：S→身分鑑別、T→完整性、R→不可否認性、
I→機密性、D→可用性、E→授權。

**已由 sec-audit 找出的實際漏洞優先列入**——那些是已證實存在的威脅，
比推測出來的更有價值。用 check-id 標註來源。

## 步驟 3：DREAD 評分

### 兩份指引採用不同算法，先選定再算

| 來源 | 算法 | 範圍 | 分級區間 |
|---|---|---|---|
| **設計指引**（表 12 範例） | 五維**相加** D+R+E+A+Di | 5–15 | 12–15 高 / 8–11 中 / 5–7 低 |
| **流程指引**（表 9 範例） | **(R+E+Di) × (D+A)** | 6–54 | 未明訂區間 |

兩份指引的內文均載乘法公式；設計指引的範例表採相加
（「3 3 2 2 2 → 12」「3 3 3 3 2 → 14」），流程指引的範例採乘法
（「2 2 2 2 3 → 30」）。

**預設採用設計指引的相加法**，理由是它有明確定義的分級區間，
稽核時對得上。**產出文件時必須在表格上方註明採用哪種算法**，
否則對方無法驗算。

若機關指定用乘法，分級區間需另行約定並一併註明。

### 評分標準

| 維度 | 高（3） | 中（2） | 低（1） |
|---|---|---|---|
| 可能傷害 D | 取得完整機敏資料或系統最高權限 | 洩漏部分機敏資料 | 洩漏系統細節資訊 |
| 可重製性 R | 可不停重製且無需等待 | 可重製但需等待 | 難以重製，或需深入知識 |
| 可刺探性 E | 不具相關技能者也可發動 | 具相關技能者可發動 | 需對弱點有深入知識 |
| 影響使用者數 A | 所有使用者 | 部分使用者 | 極低比例使用者 |
| 可發現性 Di | 公開資訊已揭露手法與漏洞 | 已有相關資訊但漏洞未揭露 | 極少用到的功能且難以發現 |

### 信心度標示（必須做）

**全部自動打分，但每個維度標示信心度。** 使用者未必是資安專家，
空白表格對他沒有用；但假裝每個數字都可靠也是誤導。

| 維度 | 預設信心 | 理由 |
|---|---|---|
| 可重製性 R | **高** | 由漏洞類型決定，程式碼看得出來 |
| 可刺探性 E | **高** | 看是否需登入、需特殊工具，程式碼看得出來 |
| 可發現性 Di | **中** | 端點是否公開看得出來，但是否已被揭露看不出來 |
| 可能傷害 D | **低** | 取決於資料敏感度，需業務脈絡 |
| 影響使用者數 A | **低** | 取決於部署規模與流量，程式碼看不出來 |

低信心的欄位**照樣填合理預設值**，並在「待確認」欄寫明：
依據什麼假設、使用者該去確認什麼。

範例（採相加法，表格上方須註明「算法：D+R+E+A+Di，區間 12–15 高 / 8–11 中 / 5–7 低」）：

| 威脅 | 來源 | D | R | E | A | Di | 風險值 | 等級 | 待確認 |
|---|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|---|
| 查詢介面遭 SQL 注入取得使用者資料 | SAST-INJ-001 | 3 | 3 | 3 | 3 | 3 | 15 | 高 | D 假設 users 表含個資；A 假設全體使用者資料在同一表 |
| 檔案讀取端點遭路徑尋訪 | SAST-INJ-003 | 2 | 3 | 3 | 2 | 2 | 12 | 高 | D 假設僅可讀設定檔非全系統；A 假設僅影響該端點使用者 |
| 缺少安全標頭導致點擊劫持 | DAST-HDR-003 | 1 | 3 | 2 | 2 | 3 | 11 | 中 | D 假設無高風險交易頁面；A 假設僅影響互動式頁面使用者 |

**產出後務必驗算一次**：相加法五欄總和必須等於風險值欄，
且等級要與區間相符。算術錯誤在稽核時很容易被抓到，且會連帶
使整份文件的可信度受質疑。

## 步驟 4：對應控制措施

每個威脅列出控制措施。已修補的引用 sec-audit 的處置；未修補的引用
`checks/` 的「過關寫法」。

一項控制措施無法把風險降到可接受時，列多項。

| 威脅 | 風險等級 | 控制措施 | 狀態 |
|---|---|---|---|
| 查詢介面遭 SQL 注入 | 高 | 改用驅動層 placeholder 參數化查詢 | 已修補（見 findings.md） |

## 輸出檔案

`security-deliverables/threat-model.md`，章節順序固定：

1. 系統概述與範圍
2. 資料流程圖（mermaid）
3. 信任邊界說明
4. 威脅清單（STRIDE 分類）
5. DREAD 評分與排序（含信心度與待確認欄）
6. 威脅與控制措施對應表
7. **待人工確認事項彙整**——把所有低信心欄位集中列出，方便逐項處理

第 7 節不可省略。它是這份文件能不能被信任的關鍵。
