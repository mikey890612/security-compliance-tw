# 行動應用 App 基本資安檢測基準勾稽表產出規則

輸出：`security-deliverables/checklist-mas.md`

資料來源三份：

| 來源 | 提供什麼 |
|---|---|
| `../controls-mas-v4.md` | 65 條的條號、條目標題、適用分類（唯一來源，不得自行判斷分級） |
| `../mapping.md` 行動端對照表 | check-id ↔ MAS 條號的對應、平台 |
| `security-audit/findings.md` | 各 check 的實際判定結果 |

**沒有 findings.md 就不要產。** 先請使用者跑 `sec-audit`。

## ⚠ 產出前必須知道的涵蓋率事實

**65 條中，目前有 39 條掛得上 check，其餘 26 條沒有。**

**那 26 條全部是流程／營運類項目**——商店發布、蒐集前取得同意、
問題回報管道、交易通知、更新公告。它們不是「還沒做」，
而是**源碼本來就判不了**：需要看實際畫面、營運流程與對外公告。
其中 16 條屬必要檢測項目。

分級分佈：

| 分級 | 條數 |
|---|---|
| L1、L2、L3 | 8 |
| L3 | 5 |
| L2、L3 | 1 |
| F | 2 |
| 參考項目 | 10 |

**這代表勾稽表的多數列會是「非程式碼可判定」或「本知識庫尚未涵蓋」，
而不是「符合」。** 產出時不可因為表格看起來空而去補判斷——
這 26 條本來就不是源碼能判定的事，補 check 沒有意義——
要做的是**列出該提供什麼證據**，見下方「流程類項目的證據指引」。

**首頁必須寫出這個涵蓋率**，否則使用者會誤以為未標「不符合」就是通過。

⚠ **上表的數字會隨知識庫擴充而變動，產出前重算，不要照抄本檔。**

```bash
cd security-compliance-tw/references && python3 - <<'EOF'
import re, pathlib, collections
mp  = pathlib.Path("mapping.md").read_text(encoding="utf-8")
ctl = pathlib.Path("controls-mas-v4.md").read_text(encoding="utf-8")
covered = set(re.findall(r'MAS (4\.\d+(?:\.\d+){3})', mp))
allc = dict(re.findall(r'^\| (4\.\d+(?:\.\d+){3}) \| ([^|]+?) \|', ctl, re.M))
gap = collections.Counter(v for k, v in allc.items() if k not in covered)
print(f"有 check 對應 {len(covered)} 條／無對應 {len(allc)-len(covered)} 條")
for k, v in sorted(gap.items()):
    print(f"  {k}: {v}")
EOF
```

## 產出步驟

1. **判定 App 類別**——依 `../profile.md` 的推導規則得出 L1 / L2 / L3，
   以及是否加測 F。**推導依據要寫進首頁**（例如「有登入、無金流 → L2」）
2. **篩選條目**——讀 `../controls-mas-v4.md`，取分類欄含該類別的條目。
   例如 L2 專案取分類為 `L1、L2、L3`、`L2、L3`、`L1、L2` 的條目
3. **參考項目一律另立區段**，見下方
4. 每個條號經 `../mapping.md` 行動端對照表**反查**對應的 check-id
5. 帶入該 check 在 `findings.md` 的判定結果
6. 找不到對應 check 的條號 → 標「非程式碼可判定，需人工確認」

### 條號一律加 `MAS ` 前綴

表格中的檢測基準條號**一律寫成 `MAS 4.1.2.3.7`**。

檢測基準與附表十的條號會字面撞車——兩者都有 `4.1.1`、`4.1.2`。
不加前綴，稽核人員會對錯表。

**同一份文件若同時列出附表十與檢測基準，兩者必須分屬不同表格，不可混列。**

## 兩種一對多，處理方式不同

### 一個條號對應多則 check

例：`MAS 4.1.4.1.1` 同時對應 `MAST-AUTH-001` 與 `MAST-AUTH-002`。

**全部通過才標「符合」。** 任一則為真漏洞即標「不符合」，
佐證欄要列出**是哪一則**造成不符合，不可只寫條號。

```markdown
| MAS 4.1.4.1.1 | 行動應用程式應有適當之身分鑑別機制，確認使用者身分 | 不符合 | MAST-AUTH-002 生物辨識未綁定金鑰（LoginVC.swift:88）；MAST-AUTH-001 通過 |
```

### 一則 check 對應多個條號

例：`MAST-RESILIENCE-005` 同時對應 `MAS 4.1.5.5.6`（混淆，F 類）
與 `MAS 4.1.5.5.5`（加殼，參考項目）。

**兩個條號各佔一列，各自填入判定結果**——不可合併成一列，
也不可因為是同一則 check 就假設兩條號結果相同。

⚠ **這一組尤其要小心：兩個條號的分級可能不同。**
`4.1.5.5.6` 是 F 類（加測時必要），`4.1.5.5.5` 是參考項目（非必要）。
合併成一列會把參考項目升格成必要項目，或反過來把必要項目降格。

目前三則 check 屬於這種情況：

| check | 對應條號 | 分級差異 |
|---|---|---|
| `MAST-RESILIENCE-002` | `4.1.5.5.9` / `4.1.5.5.8` | 皆 F |
| `MAST-RESILIENCE-003` | `4.1.5.5.7`（F） / `4.1.5.5.3`（參考項目） | **不同** |
| `MAST-RESILIENCE-005` | `4.1.5.5.6`（F） / `4.1.5.5.5`（參考項目） | **不同** |

後兩者的參考項目條號要落到「非必要檢測項目」區段，**不與 F 類列在一起**。

## 六種結果，不可混用

沿用附表十勾稽表的五種（見 `checklist.md`），另加「本知識庫尚未涵蓋」：

| 標記 | 條件 | 判斷關鍵 |
|---|---|---|
| **符合** | 對應的 check 全部通過 | 有正面證據 |
| **不符合** | 任一對應 check 判定為真漏洞且未修補 | 有負面證據 |
| **已修補** | 原為不符合，經修補後通過，附修補位置 | 有修補證據 |
| **不適用** | App 不具備該條所預設的機制 | 源碼看得出來「這件事不存在」 |
| **非程式碼可判定** | 需查證流程或營運現況，源碼無從得知 | 源碼看不出來 |
| **本知識庫尚未涵蓋** | 該條號無對應 check，且不屬上述任一種 | 我們沒做這一項 |

**「非程式碼可判定」與「本知識庫尚未涵蓋」是兩件事，不可互相取代：**

- 「商店發布」「蒐集敏感性資料前取得使用者同意」「開發者應提供回報管道」
  → **非程式碼可判定**（這些本來就不是源碼的事，任何知識庫都判不了）
- 假設某天新增了「螢幕覆蓋攻擊防護」的 check，在那之前該條號
  → **本知識庫尚未涵蓋**（源碼判得出來，只是我們還沒做）

把後者寫成前者，會讓使用者以為那是無解的項目而不去處理。

**這兩類與「不適用」都絕對不可標成「符合」。** 沒有正面證據標符合就是編造。

## 表格格式

```markdown
| 條號 | 條目標題 | 適用分類 | 結果 | 佐證 |
|---|---|---|---|---|
| MAS 4.1.2.3.7 | 敏感性資料應儲存於受作業系統保護之區域，以防止其他應用程式未經授權之存取 | L1、L2、L3 | 已修補 | MAST-STORAGE-001；LoginActivity.kt:42 改用 EncryptedSharedPreferences |
| MAS 4.1.2.1.1 | 行動應用程式應於蒐集敏感性資料前，取得使用者同意 | L1、L2、L3 | 非程式碼可判定 | 需確認同意流程的實際畫面與時序 |
```

⚠ **「條目標題」欄必須逐字照抄 `../controls-mas-v4.md`，不得改寫或縮短。**

理由同附表十勾稽表：檢測實驗室與稽核人員是拿官方條文逐字比對的。
產出後**逐項比對文字是否與來源一致**，不只比對條數——
條數對但文字被改寫，肉眼掃過不會發現。

需要補充說明時寫進「佐證」欄，不要動「條目標題」欄。

「適用分類」欄同樣照抄來源，不要自行換算成「必要／非必要」。

## 區段結構

固定四段，順序不變：

```
一、必要檢測項目（依 App 類別篩選後的條目）
二、F 類加測項目          ← 僅在使用者勾選「將送 F 類加測」時出現
三、非必要檢測項目（參考項目）
四、涵蓋率與未涵蓋條目說明
```

**第三段的標題必須寫明「非必要」。** 參考項目在檢測基準中不是必要條件，
與必要項目混列會讓受測方誤以為全部都要做。

**第四段是本文件最重要的一段**，內容：

1. 65 條中有多少條有 check 對應、多少條沒有
2. 沒有對應的條目按分級列出條數（讓讀者知道漏掉的是不是必要項目）
3. 明寫「未標『不符合』不等於通過」

範例：

> 本次勾稽的 44 條必要項目中，12 條有源碼層級的判定依據，
> 其餘 32 條標為「非程式碼可判定」或「本知識庫尚未涵蓋」。
> **未標「不符合」不代表該條通過**——多數條目需由檢測實驗室以
> 動態測試、人工審查或文件查核方式判定，本表無法取代。

## 首頁必載事項

四項，缺一不可：

1. **App 類別的判定結果與推導依據**（例如「有登入功能、無線上金錢交易 → L2」），
   以及是否加測 F 類
2. **本表由源碼靜態分析產出，未執行任何檢測工具**——
   本專案明文不執行掃描工具，這一點必須在首頁講清楚
3. **涵蓋率**（見第四段）
4. **本表不等於檢測報告**——檢測基準的正式檢測由通過認可的檢測實驗室執行，
   本表僅供送檢前自我檢視與缺口盤點

## 不可做的事

- **不可把 `MAS` 欄有值當成該條「符合」。** 對照關係只說明「這則 check 與這條有關」，
  判定結果來自 `findings.md`
- **不可為了讓表格好看而把「非程式碼可判定」改成「符合」。**
  這是本專案的第一原則：看不到證據的項目不可標符合
- **不可自行為未涵蓋的條號生成判定。** 標「本知識庫尚未涵蓋」，
  不要憑印象推測該項是否做到
- **不可縮短或改寫條目標題。** 見上方
- **不可在同一張表混列附表十與檢測基準的條號。** 見上方
